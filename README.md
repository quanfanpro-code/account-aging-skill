# 📘 往来账龄：把账表交给助手，用聊天拿到结果

这个技能用来回答：**截至某一天，每个客户还欠我们多少钱、我们还欠每个供应商多少钱，这些钱分别形成了多久？**

你提供账表，告诉智能助手计算日期和要求。助手负责读表、计算、核对，最后交付一份带计算依据的 Excel 文件。你不用打开原来的桌面程序，不用写代码，也不用填写技术参数。

## 🚀 第一次使用，只做这三步

1. **给资料。** 把序时账交给助手，或告诉它你电脑上的文件、文件夹位置。有科目余额表、期初余额和期初账龄的，也一起提供。
2. **说要求。** 至少说清是哪家公司、算到哪一天。已经有完整历史且期初为零的，直接说明；有几个计算日期，也可以一次说完。
3. **收结果。** 助手核对后另存一个结果文件。打开文件，先看底部标签为蓝色的账龄结果表，再看备注和必要明细。

你可以直接这样说：

> 请用附件中已经整理好的序时账，计算这家公司截至2025年12月31日和2026年8月31日的往来账龄。我们有完整历史，期初余额为零。分成1年以内、1—2年、2—3年、3—4年、4—5年、5年以上。应收票据和应付票据都不纳入。请保留计算依据和特殊事项，结果另存，不要覆盖源文件。

想把应收票据一起计算时，把其中“应收票据和应付票据都不纳入”改成“应收票据也纳入，转科目时保留原始账龄”。助手会继续核查票据类型和对应关系。

**不用一次把所有细节都想好。** 分档等没有另行指定的事项，会采用下文说明的默认规则；真正影响结果、又无法从资料查明的事项，助手会集中说明。

## 🧩 使用前，需要什么环境？

需要一台 Windows 电脑，以及一个能够使用技能、读取账表和执行计算的智能助手。本技能包含自己的计算工具，不要求先安装原来的桌面程序。

如果助手还没有装这个技能，把[技能仓库](https://github.com/quanfanpro-code/account-aging-skill)交给它，告诉它：“请安装这个往来账龄技能，之后通过对话帮我计算。”具体安装工作交给助手处理。

如果本机缺少必要的运行组件，助手应说明缺什么、影响什么，再按你的授权处理。只会聊天、无法读取资料或执行计算的环境，不能凭一段文字说明就当作已经完成计算。

## 📂 资料怎么准备？

### 最重要的是序时账

序时账就是一笔笔记账记录。通常需要下面这些内容，列名不必完全一样，助手负责识别：

| 资料里的内容 | 用来做什么 |
|---|---|
| 记账日期 | 判断是否在计算期间内，以及这笔钱形成了多久 |
| 科目编码、科目名称 | 区分应收、应付、预收等不同往来 |
| 客户或供应商名称 | 确定每一笔属于谁 |
| 借方金额、贷方金额 | 计算新增、收回、支付和剩余余额 |
| 摘要 | 辅助识别暂估、冲回、转科目等业务 |
| 凭证号 | 找到对应记账记录，核对转科目关系 |

有票据业务时，最好同时有**票据类型和票据号**。票据号相当于每张票据的身份标识，可以避免把甲票据的收款冲到乙票据上。

不同系统的表头不一样，不需要你自己改成固定模板。助手先查看原表，再整理计算输入；原文件保留。

### 期初资料分两种情况

| 你的情况 | 怎么处理 |
|---|---|
| 有公司成立以来或足以覆盖全部余额的完整历史，且确认起点余额为零 | 直接从零计算，不另外索取一张零余额表 |
| 只有部分年度的序时账，之前已经存在余额 | 提供计算起点的余额、起点日期，以及能证明这些余额形成多久的资料 |

只有期初余额、没有期初账龄时，可以知道“还剩多少钱”，却未必能知道这些钱真实形成了多久。助手应说清依据和影响，不能把历史余额全部当成最近新增，也不能随便编一个旧日期。

科目余额表可以帮助核对余额，但**只有一张期末余额表，通常不足以还原每笔余额的账龄**。

## 🧾 可以计算哪些科目？

| 往来科目 | 日常含义 |
|---|---|
| 应收账款 | 客户已经买货或接受服务，尚未付清的钱 |
| 预付账款 | 我们先付给供应商、尚未结清的钱 |
| 其他应收款 | 其他应该收回的往来，例如符合账面分类的押金、借款 |
| 合同资产 | 账面记在合同资产中的款项 |
| 应付账款 | 我们采购货物或服务后，尚未付清的钱 |
| 预收账款 | 客户先付给我们、尚未结清的钱 |
| 其他应付款 | 其他应该支付的往来 |
| 合同负债 | 账面记在合同负债中的款项 |
| 应收票据 | 可以纳入，并追踪与应收账款之间的账龄衔接 |

不属于本次范围的存货、成本、费用，以及坏账准备等，不混入往来本金计算。**应付票据目前不在支持范围内。** 已经明确排除应收票据的任务，也不会擅自把它加回来。

## ⚙️ 从原账到结果，具体怎么计算？

### ① 先确定范围，再检查资料

助手确认公司、计算日期、科目范围、期初和分档。一个任务可以算多个日期，每个日期只使用当日及以前的记录，不拿以后的收付款提前冲减过去的余额。

之后检查日期、金额、列名和单位名称，确定哪些行要纳入。能够从原账查清的问题先查原账；需要你决定的，说明具体单位、金额和影响，不把一大堆“待核实”直接退给你。

### ② 按单位、按科目分别整理

同一单位的记录放在一起，不同单位分开计算。单位名称相似，只是核查线索，不能直接当成同一家公司。

目前保留名称疑似重复的识别和确认能力。完整的往来单位名称整理技能，等单独完成并提供后再包入，**当前不能当作已经具备完整归一化能力**。这里的“归一化”就是把经证据确认属于同一家单位的不同称呼统一起来。

### ③ 收付款默认先冲较早形成的余额

例如，某客户先欠1,000元，后来又欠2,000元，之后付款800元。默认先冲前面的1,000元，因此剩下“较早的200元”和“较后的2,000元”，分别按各自形成日期计算。

这是按发生顺序分配收付款的计算办法，并不表示已经取得逐张发票的实际核销关系。有特殊结算安排时，应提前告诉助手，由它核对适用范围。

### ④ 暂估冲回后重新入账，等额部分接着算

“暂估”可以理解为业务已经发生，但正式发票等尚未到齐，先按估计金额记账；收到资料后再冲回、正式入账。

例如，2023年暂估应付1,000元，2025年冲回这1,000元，再按正式发票记入1,130元。本技能当前按下面的规则处理：

- 承接的1,000元保留2023年的原账龄。
- 新增差额130元从2025年正式入账日计算。
- 后续实际付款、退款或退货，按真实业务冲减余额。

暂估可以写在科目名称中，也可以写在摘要中。冲回摘要没有“暂估”二字、但明确引用原暂估凭证时，会在同单位、同科目中核对原凭证和金额；对应不唯一时不猜测。

哪些行被认作暂估、为什么这样认，以及承接了多少，都保留在依据表中。

### ⑤ 应收账款转成应收票据，符合口径时保留原账龄

例如，客户2023年形成的欠款，2025年改用商业承兑汇票结算。在适用的连续计龄口径下，转入票据的这部分仍追溯2023年的债权，不能仅因为2025年收到票据就全部算成新款。之后转回应收账款时，也继续保留已追踪的原账龄。

应收账款和应收票据仍分别列示。部分兑付只冲减对应金额；有票据号时，优先核销对应票据。

自动关联要求转出、转入记录为**同一天、同一凭证、同一结算客户**。同一天但不同凭证的，助手可以依据明确资料指定关系。**跨日的两边分录，目前不支持直接承接。**

银行承兑或类型不明的票据，需要结合资料确定口径，不能只看“银行”两个字就认定原债权已经结清。具体依据和适用范围见[票据连续计龄规定](references/票据连续计龄规定.md)。

### ⑥ 方向相反的余额，转到对应科目并标明

例如，应收账款通常表示客户欠我们钱；如果某单位在这个科目出现贷方余额5,000元，可能需要按程序口径转入预收账款列示。

本技能会按对应科目重新追溯计算，并在结果表最后的**备注**中醒目标明原科目和金额。余额构成依据表中，也会标明哪些剩余款项来自这次重分类，方便直接查看。

这是结果中的计算列示，不会修改原账。

### ⑦ 同单位成对往来，按净额列示并留痕

例如，同一客户应收10,000元，同时预收3,000元，按本程序口径对抵后，结果列示应收7,000元，并在备注写明对抵3,000元。对抵时先冲减较老的剩余款项。

成对范围是：应收与预收、预付与应付、其他应收与其他应付、合同资产与合同负债。不同单位不对抵，不相关的科目组合不混抵；没有单位名称的记录，也不能直接认定属于同一个人或同一家公司。

这里说明的是程序的计算展示规则，不代表已经判断财务报表在所有情形下都满足法定抵销条件。

### ⑧ 核对余额和分档，再保存结果

助手核对原账发生额、计算余额和各档金额，确保分档加总与期末余额一致。发现不平时先查原因，不靠调整尾数或编造期初把差额抹平。

计算依据、重分类、对抵、暂估和票据承接等记录放在结果文件后面的工作表中。源文件不覆盖，交付时保留一份明确的最终结果，避免混淆版本。

## 📅 默认分成哪几档？

默认按365天算一年，边界当天归前一档：

| 显示名称 | 对应天数 |
|---|---|
| 1年以内 | 0—365天 |
| 1—2年 | 366—730天 |
| 2—3年 | 731—1,095天 |
| 3—4年 | 1,096—1,460天 |
| 4—5年 | 1,461—1,825天 |
| 5年以上 | 1,826天及以上 |

想用其他分档，直接说“请按……分档”。助手会核对区间是否完整、有无重复。这里计算的是**款项形成至今多久**；“超过合同付款期限多久”属于逾期天数，不能混为一谈。

## 📊 拿到文件后，按这个顺序看

**先看蓝色标签的结果表。** 一个计算日期通常对应“账龄计算结果”；多个日期分别对应各日期的账龄结果表。

| 工作表 | 什么时候看 | 主要看什么 |
|---|---|---|
| 账龄结果表，标签为蓝色 | 先看这里 | 各科目、各单位期末余额、分档金额，以及最后的备注 |
| 特殊事项，如有 | 接着看影响理解的例外 | 特殊处理采用了什么口径、理由是什么；当前自动记录的典型事项包括经明确判断不连续计龄的票据转入 |
| 期末余额构成及账龄依据 | 想追问“这个余额怎么来的” | 每笔剩余金额、来源日期、账龄天数和重分类等说明 |
| 原账勾稽 | 想核对“算出来和账上是否一致” | 期初、借贷发生额、期末余额和差额；“勾稽”就是前后数字能否对得上 |
| 重分类记录、对抵记录 | 结果备注出现这些处理时 | 从哪个科目转到哪个科目、转了多少，或对抵了多少 |
| 暂估识别依据、内部转科目记录 | 存在暂估转正式时 | 为什么认作暂估、冲回与正式入账如何承接 |
| 票据连续计龄依据 | 存在应收与票据转科目时 | 哪部分沿用原债权日期、对应凭证和票据是什么 |
| 计算用序时账、计算用期初，如有 | 需要回查原始记录时 | 实际用于计算的资料；补充名称等有依据的输入处理，应保留理由 |
| 处理确认记录、参数说明等 | 想核对本次采用的规则时 | 名称和科目归属的处理决定、截止日期和分档等 |

没有发生的事项，不要求生成空表。依据表用于解释结果，不能用一堆表格代替一张能直接看懂的最终结果表。

## 💬 常见问题，直接这样告诉助手

| 你遇到的情况 | 可以怎么说 |
|---|---|
| 同时算两个日期 | “请同时算2025年末和2026年8月末，放在同一份文件里。” |
| 历史完整、起点为零 | “从公司成立以来的账都在这里，期初余额为零。” |
| 不计算票据 | “本次排除应收票据和应付票据。” |
| 结果里出现异常方向 | “请说明备注里的重分类从哪里转来、金额是多少。” |
| 想追查某单位的金额 | “请沿着余额构成依据，解释这家单位的剩余余额。” |
| 两个名称可能是同一家公司 | “请结合明细科目、摘要和其他证据核实，不要只凭名字相似就合并。” |
| 日期或金额识别失败 | “请先定位原表具体行并查原因，说明会影响哪些结果。” |

遇到资料缺失或不支持的业务，助手应说明**具体哪里受影响、已经查过什么、还缺什么**。能继续独立计算的部分继续处理，但不能把受影响部分写成已经准确完成。

## 🚧 目前明确的边界

- 完整的单位名称归一化技能尚未接入，等单独提供后再自包含打包。
- 应收账款与应收票据的跨日转科目，暂不支持直接承接。
- 不计算应付票据，也不自动计算坏账准备金额。
- 不自动判断背书、贴现后原债权是否应从账面消失；账面漏记、错记的复杂事项须先核查，不能靠账龄计算自动补成正确会计处理。
- 不把不同币种直接相加。计算输入应统一为同一本位币金额，即公司记账时统一使用的货币口径。
- 缺少原始记录和可靠期初账龄时，不虚构更早的债权日期。

## ✅ 做过哪些验证？

已经验证普通往来、暂估承接、票据双向转科目、多批来源、部分收款、指定票据核销、期初分档、截止日期、重分类、对抵，以及实际文件导出。模拟测试用来检查计算和文件功能，不等同于所有真实业务都已经覆盖。

还使用达尔文技能做过独立评估：三个常见场景实际执行，三位评审分别比较新旧说明后，一致支持保留本轮改进。具体发现和修正见[评估记录](评估记录.md)，不把主观评分当成计算准确率。

另用智仁合完整序时账做过本机复算：完整读取24,984行，纳入4,857行往来，核对两个时点共887个原账分户。最终余额、六档账龄和余额来源日期均与原交付结果一致。该次按项目要求排除了票据，因此不能据此声称真实票据业务也已完成验收。客户账表与结果不放入公开仓库。
